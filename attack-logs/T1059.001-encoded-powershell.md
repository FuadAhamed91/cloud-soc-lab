# Command and Scripting Interpreter: PowerShell (encoded) — T1059.001

| Field | Value |
|-------|-------|
| ATT&CK | T1059.001 — Command and Scripting Interpreter: PowerShell |
| Tactic | Execution |
| Platform | Windows |
| Endpoint | DESKTOP-MTJVV2L (agent 002) |
| Date | 2026-09-18 |

## Simulation
Attacker runs an obfuscated (base64-encoded) PowerShell command to hide intent from simple filters.
```
powershell -EncodedCommand VwByAGkAdABlAC0ATwB1AHQAcAB1AHQAIABsAGEAYgAtAHQAMQAwADUAOQAtAHQAZQBzAHQA
```
(Decodes to a harmless `Write-Output lab-t1059-test`; the encoded *method* is the signal.)

## Telemetry produced — Sysmon
Sysmon **Event ID 1 (Process Create)** captured the full command line, hashes, parent process,
and even tagged the technique (sysmon-modular config):
```
RuleName: technique_id=T1059.001,technique_name=PowerShell
CommandLine: powershell.exe -EncodedCommand VwByAGk...
User: DESKTOP-MTJVV2L\fuad  IntegrityLevel: High
Hashes: SHA256=64DD55E1...,MD5=6726185B...,IMPHASH=E3007C8E...
ParentImage: powershell.exe
```
Windows' default logging does **not** record process command lines — this detail exists only
because Sysmon is installed.

## Detection result
Fired on a **default Wazuh rule** — no custom rule needed:

| Rule ID | Level | Description |
|---------|:-----:|-------------|
| 92057 | 12 | Powershell.exe spawned a powershell process which executed a base64 encoded command |

## Verdict
**Caught by default (via Sysmon).** Wazuh's built-in PowerShell rules are strong — but they only
work because Sysmon supplies the command line. Good example of default coverage being *uneven*:
Linux techniques tested here were gaps (custom rules written); Windows PowerShell is well covered.

## False-positive check
Legitimate admin/automation sometimes uses encoded PowerShell, so 92057 can false-positive in
some environments — but base64-encoded PowerShell is unusual enough that a level-12 alert is
justified and worth triaging.
